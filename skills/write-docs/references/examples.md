# 写作与评审示例

## 删除空话，保留事实边界

原文：
> 为了进一步全面提升系统的稳定性和可靠性，我们引入了先进的异步处理机制，从而显著优化整体性能。

问题：没有说明改了什么、为什么有效、是否验证；多个褒义词没有证据。

已有设计、没有测量时：
> 请求入队后立即返回，消费者在后台执行任务。这个设计缩短了请求等待执行结果的时间，但任务总耗时仍取决于排队和执行速度，需通过压测验证。

有真实测量时才补充具体结果、时间窗、样本、对照条件和来源。不要用编造的百分比替换模糊形容词。

## 用渐进解释处理复杂概念

读者不了解“幂等”时，先讲：
> 同一笔付款请求重复发送，也只扣一次钱。这种重复请求不改变最终效果的性质称为幂等。

再讲如何识别同一请求、保存处理结果，以及重试与并发的边界。不要在读者还不知道问题是什么时先堆术语和实现细节。

## 图表取舍

三个方案按成本、时延和维护难度比较，应提供对比表；表格前给选择问题，表格后解释影响选择的关键取舍。即使文字已完整描述各方案，也不能据此省略便于横向阅读的比较表。

“收到请求 → 校验 → 成功入队或返回错误”可用短句说明；存在多次重试、超时和补偿分支时，应提供流程图。长篇系统设计先给总览图，再在关键交互附近给时序图，让读者先看到全貌再理解细节。

如果一张图有十五个无标注箭头，不能因“有架构图”加分。应标注关系、分组或拆图，让读者回答“谁调用谁、数据往哪走、失败在哪里处理”。

## 评分的边界情况

1. **短小的单一概念说明，无数字也无图片**：若内容不存在需要视觉呈现的复杂关系，正文能独立解释概念和边界，各维度均可得 4。对于复杂长文，必须另查总览和必要图表是否齐全。
2. **排版精美，声称性能提升 40% 却无依据**：若它影响决策且被表述成实测事实，属于阻塞项；高可读性不能抵消。
3. **明确标注假设的探索备忘录**：若目的是提出待验证方向，假设合理且有验证路径，可通过；若用户要求确定可上线方案，则证据仍不足。
4. **字数少但省略授权前提的操作指南**：简洁不能补偿无法执行，先补齐前提。
5. **数据由 20% 升至 30%**：增加 10 个百分点，相对增长 50%；应根据读者问题选择表述，保持分母和时间口径一致。
6. **三种架构的长篇比较，只有连续段落**：即使事实准确，也应增加按关键决策维度组织的对比表；补齐前视觉维度最高 2 档，不能正式准出。

算分示例：六维档位为 4、3、4、3、3、3 时，总分为 85.0。只有同时满足无阻塞、所有核心读者问题可答，才判“通过”；总分不是唯一门槛。

## 载体与阅读引导示例

- **多层系统架构**：用画板把客户端、服务、队列和存储按边界分组，以组件图标和带标签的连线表达职责与数据流；旁边用短段落解释关键取舍。不要为了迁就自动布局把所有组件挤进同一条链。
- **不同策略下的请求路径**：需要读者切换策略观察差异时，可用 HTML 内容块；默认状态先展示主要路径，并在正文给出可独立理解的结论。
- **多模块分析**：开篇高亮块写全局判断和依据，各章节用一句话说明局部发现，随后展开证据。若全局结论是“排队占主要等待时间”，各章分别解释排队、执行和重试，而不是每章重复同一句总结。
- **证据有限的结论**：高亮“当前样本显示等待主要发生在队列中；尚未验证高峰时段”，不能只保留“瓶颈已定位”来增强视觉冲击。
